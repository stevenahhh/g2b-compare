# g2b-similar-product-search - Work Plan

## TL;DR (For humans)

What you'll get: 나라장터 공식 데이터의 로컬 스냅샷에서 물품명·카테고리·옵션/규격·가격을 빠르게 검색하고, 검색된 각 물품마다 근거가 보이는 유사 물품 3개를 비교하는 단일 사용자용 웹 앱임. 추가선택품목도 독립 물품으로 검색되며, 확인된 관계만 출처와 함께 표시됨.

Why this approach: 검색할 때 외부 API나 동적 쇼핑몰 화면을 호출하지 않고 로컬 SQLite와 버전 고정 랭킹을 사용하므로 빠르고 재현 가능함. 공식 API의 일일 호출 한도와 D-1 데이터 특성은 체크포인트 배치 동기화와 마지막 정상 스냅샷 유지로 흡수함.

What it will NOT do: 나라장터 화면 스크래핑, 근거 없는 본품-추가품목 연결, AI 임베딩/LLM 랭킹, 자동 발주, 클라우드·다중 사용자 운영은 포함하지 않음.

Effort: Large
Risk: High - 인증 성공 응답 스키마와 속성 API HTTPS 동작이 아직 실제 키로 검증되지 않았고, 개별속성은 물품별 호출이라 전체 보강에 시간이 걸릴 수 있음.
Decisions to sanity-check: 세 종류의 현재 계약품목을 모두 포함함. 가격은 단위가 명확한 현재 계약가격만 사용함. 상세분류·물품명은 정확히 일치해야 비교 후보가 됨. Windows에서는 설치 프로그램이 아니라 로컬 실행 스크립트로 제공함.

Your next move: 이 계획을 `$start-work`로 실행하면 됨. 아래는 구현자가 추가 질문 없이 따를 전체 실행 명세임.

## Scope
### Must have

- Python 3.12 이상, FastAPI, Jinja2, 소량의 로컬 vanilla JavaScript, SQLite WAL/FTS5를 사용하는 단일 프로세스 앱임. 기본 바인딩은 `127.0.0.1:8765`이며 공개 인터페이스 바인딩을 거부함.
- 검색 폼은 `물품명` 필수, `상위/상세 카테고리`, `옵션/규격`, `목표가격(원)`, `가격단위`, `가격 허용범위(기본 25%)`를 가짐. 물품명·분류 exact 후보 전체를 허용범위 여부와 관련도 순으로 페이지당 50개씩 제공함.

## Verification strategy
> Zero human intervention during verification - all commands and verdict calculations are agent-executed. Human-authored gold labels are a provenance-stamped external prerequisite; verification only validates and consumes the supplied immutable corpus.
- Test decision: TDD. `pytest`, `pytest-asyncio`, `Hypothesis`, `respx`, `Playwright`, `ruff`, `basedpyright` 사용함. 각 todo는 먼저 해당 실패 테스트가 예상 이유로 실패한 로그를 남기고 최소 구현 후 같은 테스트가 통과해야 함.
- 공통 품질 명령: `uv sync --frozen && uv run ruff format --check . && uv run ruff check . && uv run basedpyright && uv run pytest -q`.
- Todo N의 정확한 RED/GREEN 계약: 계획의 `test_happy`와 각 failure ID는 `tests/acceptance/test_todo_N.py`에서 정확히 한 JUnit node로 정규화됨. 먼저 `uv run pytest tests/acceptance/test_todo_N.py -q --junitxml=<attemptDir>/task-N-red.xml`을 실행하며 RED는 모든 node가 `tests/acceptance/expected-failures.json`의 assertion class+message regex로 failure, pass/skip/error 0건, exit 1이어야 함. 구현 뒤 출력 경로만 `task-N-green.xml`로 바꾸며 GREEN은 동일 node ID 집합 전부 pass, skip/failure/error 0건, exit 0이어야 함. happy 단독은 `::test_happy`, failure 전체는 `-k failure` selector로 실행함. 각 `<attemptDir>/task-N-manifest.json`은 `{schema_version:"1",todo:N,plan_sha256,base_commit,green_commit,commands:{red:{argv,exit_code},green:{argv,exit_code}},nodes:{node_id:{scenario_id,red_outcome,red_failure_class,red_message_sha256,green_outcome}},artifacts:{relative_path:sha256}}`임. `tools/audit_release.py --strict`는 계획·expected-failures·task manifest·RED/GREEN JUnit의 scenario ID와 1:1 node cardinality, failure signature, plan/commit/artifact SHA를 강제함.
- 외부 네트워크는 `tests/live/`만 허용함. 핵심 catalog와 개별속성의 승인키 success fixture·HTTPS·quota manifest가 모두 없으면 Todo 5 이후로 진행하지 않고 계획 실행을 BLOCKED로 판정함. SKIP은 로컬 코어 개발 상태일 뿐 실제 API 동기화나 전체 완료로 인정하지 않음.
- fixture·E2E·성능 시험은 네트워크를 차단하고 고정 시계·고정 난수 seed·임시 SQLite를 사용함.
- 비밀검사: `rg -n -i "(serviceKey|인증키|일반인증키)\\s*[:=]\\s*[^[:space:]&]{16,}" . --glob '!docs/reference/*.docx' --glob '!var/*'` 결과 0건이어야 함.
- 데이터 안전검사: 원본 DOCX와 세 XLSX의 구현 전후 SHA-256이 같아야 하며 `var/`, `.env`, raw snapshot은 Git 추적 대상이 아니어야 함.
- Evidence: `<attemptDir>/task-<N>-g2b-similar-product-search.<ext>` 사용함. `<attemptDir>`는 ulw-loop 실행 시 현재 attempt 디렉터리, 그 외에는 `.omo/evidence/g2b-similar-product-search/`임.

### Contract probe state machine

- DISCOVER 전에 `docs/account-quota-observed.json`이 필수임. `uv run python -m g2b_compare.contracts.quota --input <external-account-export>`가 raw account export를 memory-only로 읽고 key/PII를 redaction한 뒤 service ID, operation scope, approved status, daily quota, reset timezone/window 또는 `unknown`, observed_at, source SHA만 기록하며 raw를 복사하지 않음. ShoppingMall 5개와 separately approved attribute operation의 row가 모두 있어야 함. attribute account row가 없으면 attribute HTTP call 0회로 BLOCKED임. effective ceiling은 `max(0, quota-max(ceil(quota*0.1),100))`이고 rolling 24h를 항상 적용하며 reset window가 관측되면 provider-window count도 동시에 ceiling 미만이어야 함. 해당 operation의 남은 ceiling이 DISCOVER 1회+VERIFY 2회 최소 3 attempts보다 작으면 HTTP 0회로 BLOCKED임.
- Todo 2의 각 operation은 `DISCOVER → VERIFY_SCHEMA → VERIFY_LIMIT → VERIFIED` 상태를 따름. 각 outbound call과 transient retry는 Todo 3 `api_call_ledger` reservation을 먼저 1개 소비하며 operation당 총 5 HTTP attempts를 넘지 않음. DISCOVER는 아래 D1→D3 후보를 순서대로 실행하고 첫 HTTP/envelope 정상+non-empty item에서 즉시 나머지 discovery 후보를 건너뜀. 세 후보가 모두 empty거나 transient retry 때문에 남은 attempt가 VERIFY 2회를 수행하기에 부족하면 즉시 BLOCKED임.
- VERIFY_SCHEMA는 발견된 동일 filter/window를 page 1,size 100으로 호출해 required fields, stable identity, 동일 envelope를 확인함. VERIFY_LIMIT는 동일 filter/window를 문서상 maximum request candidate, 단 1000 이하로 호출해 stable identity를 다시 확인함. 응답의 reported page size가 명시적으로 존재하고 exact 1..1000일 때만 accepted/observed size로 사용함. 두 verification 모두 non-empty여야 `live_observed`; empty, schema/key 변화, missing/invalid reported page size, unproven limit은 BLOCKED임. 401/403, HTTP downgrade/redirect, unknown quota는 어느 상태에서든 즉시 BLOCKED; 429/5xx/timeout retry는 다음 attempt를 소비하고 5회 내 VERIFIED에 못 가면 BLOCKED임.

| operation family | D1 | D2 | D3 |
| --- | --- | --- | --- |
| three contract operations | valid workbook `prdctIdntNo` 1, KST today 1-day, page 1,size 1 | same ID, last 31 days,size 1 | no ID, last 1 day,size 1 |
| registration history | KST yesterday 1-day,page 1,size 1 | last 31 days,size 1 | last 365 days,size 1 |
| delivery detail | KST yesterday 1-day,page 1,size 1 | last 31 days,size 1 | last 365 days,size 1 |
| individual attributes | sorted valid workbook product ID 1,page 1,size 1 | sorted valid ID 2,size 1 | sorted valid ID 3,size 1 |

- valid workbook IDs는 Todo 4가 추출한 값을 문자열 오름차순으로 사용함. operation이 product-ID filter를 공식 계약상 지원하지 않으면 contract family D1/D2를 동일 날짜 window의 no-ID probe로 실행하고 이유를 manifest에 기록함. VERIFIED manifest는 discovery candidate, 모든 attempt ledger ID, retry, selected filter/window, required field set, stable key fields, schema fixture SHA, VERIFY_LIMIT request candidate, exact response-reported page size 1..1000에서 얻은 accepted/observed size와 quota scope/reset source를 필수로 가짐.

### UI state matrix

| state token | trigger | HTTP/DOM behavior | fixed Korean copy |
| --- | --- | --- | --- |
| `initial` | no submitted query, active release exists | 200, form only | `검색 조건을 입력하세요` |
| `loading` | enhanced fetch in flight | existing results remain, `aria-busy=true` | `검색 중` |
| `no-active-snapshot` | no active release | 503, no fabricated rows | `검색 데이터가 아직 준비되지 않았습니다` |

| `sync-failed-last-good` | submitted valid query with matches, latest sync failed, and active release exists | 200 last-good + highest-priority banner | `최근 동기화에 실패하여 이전 데이터를 표시합니다` |

| `incompatible-price` | missing/ambiguous/different price basis | price badge | `가격 단위 비교 불가` |

- request pipeline과 primary state는 1) submitted basic shape/cross-field `validation-error`, 2) `fatal-error`, 3) `no-active-snapshot`, 4) unsubmitted `initial`, 5) submitted DB-backed semantic `validation-error`, 6) `sync-failed-last-good`, 7) `stale`, 8) `no-matches`, 9) `current-results` 순서임. unsubmitted+healthy active는 freshness/sync 실패와 무관하게 form-only `initial` primary이며 실제 freshness/sync predicate는 `data-statuses`와 form banner에만 표시함. basic invalid는 DB 상태와 무관하게 partial/JSON 422, no-JS form 200; semantic invalid는 healthy active DB가 있을 때만 같은 HTTP 규칙임. DB/index corruption은 500, healthy DB+no active는 503임. `primary-state`는 하나이고 HTTP는 이것만 따름. `data-statuses`는 모든 true predicate를 ASCII 정렬해 `sync-failed-last-good stale partial-attribute`처럼 공존 가능함. forbidden은 `fatal-error`+result token, `no-active-snapshot`+result/row token, `validation-error`+result token, `current-results`+`stale|sync-failed-last-good|no-matches`, `initial`+submitted/result token임. `loading`은 safe existing page 위 client overlay로만 허용되고 validation/fatal/no-active와 공존하지 않음. generated truth-table test가 submitted/unsubmitted×DB×freshness×sync×match의 primary/status/banner/HTTP와 모든 permitted/forbidden pair를 검증함.
- CSS는 `html,body,body *,body *::before,body *::after{font-weight:400!important}`를 적용하고 템플릿에 `<b>`/`<strong>`을 사용하지 않음. Playwright는 모든 visible text-bearing element, `th,label,legend,summary,input,select,option,button`, non-empty `::before/::after`의 computed weight 400을 1440×900·1024×768·no-JS에서 전수 검사함.

### Ranking formula v1

- 양의 scalar `x,y`는 `value_sim(x,y)=exp(-abs(ln(x/y))/ln(1.25))`임. 같은 relation shape의 유한 range는 lower/upper bound `value_sim` 평균임. relation shape가 다르거나 dimension 불일치, 0/음수, unsupported compound이면 structured edge 없음이며 해당 raw span은 lexical feature에 남김.
- eligible structured edge weight는 그 scalar/range `value_sim` 하나임. 모든 edge weight 합을 최대화하는 bipartite one-to-one matching을 쓰고 동률 matching은 정렬된 `(anchor_span_start,candidate_span_start)` pair list의 lexicographic minimum임. anchor parsed spec 집합 `Q(a)`에 대해 `U(a,c)=sum(edge_weight for matched anchor specs)/|Q(a)|`; unmatched anchor spec은 0이며 anchor spec이 없을 때만 U inactive임.
- `L=.50*cosine(tfidf_word_1_2)+.50*cosine(tfidf_char_wb_3_5)`, `F=.50*token_set_ratio/100+.50*token_sort_ratio/100`임. `P=exp(-abs(ln(price_a/price_c))/ln(1.25))`이며 양쪽 positive KRW와 canonical unit/basis가 같을 때만 계산함. anchor price는 active인데 candidate price가 없거나 호환되지 않으면 `P=0`; anchor price가 없으면 P inactive임.
- activity는 `A_L=A_F=1` iff anchor option text non-empty, `A_U=1` iff `|Q(a)|>0`, `A_P=1` iff anchor가 positive comparable price를 가짐. `D=.35A_L+.20A_F+.35A_U+.10A_P`; `S=(.35A_LL+.20A_FF+.35A_UU+.10A_PP)/D`임. `D=0`이면 `S=null`과 `no_comparison_evidence`임. candidate-side 누락은 active weight를 제거하지 않고 해당 feature 0임.
- evidence bit/ratio는 `B_L=B_F=1` iff candidate option text non-empty else 0, `B_U=matched anchor spec count/|Q(a)|` when `A_U=1` else 0, `B_P=1` iff candidate price가 anchor와 실제 비교 가능 else 0임. `coverage=(.35A_LB_L+.20A_FB_F+.35A_UB_U+.10A_PB_P)/D`; `D=0`이면 coverage도 null임. coverage는 설명용이며 S에 다시 곱하지 않음.
- raw `L,F,U,P,S,coverage`와 raw absolute log price distance를 Decimal round-half-even 6자리로 각각 quantize한 후 `S DESC NULLS LAST, U DESC NULLS LAST, L DESC NULLS LAST, F DESC NULLS LAST, price_distance ASC NULLS LAST, product_id ASC`로 정렬함. 같은 version 입력은 byte-identical ordered IDs를 내야 함.

### Operational storage decision
- SQLite is the canonical operational store for search, price comparison, attributes, provenance, sync cursors, and release pointers. JSON/JSONL files are never the primary searchable database.
- Provider response bytes remain immutable content-addressed gzip blobs under `var/raw/sha256/`; SQLite stores their path, SHA-256, content type, page/run provenance, and normalized rows. JSONL is limited to deterministic evaluation/export packages.
- Main-product/additional-purchase relationships are normalized rows (`curated_relations`) plus delivery-event observations (`option_role_observations`), never paths to nested JSON documents. Unverified delivery roles must not be promoted to a parent-child relation.
- Images are optional enrichment only after a stable official image URL field is observed in a VERIFIED source contract. Until then the UI uses a local placeholder. If verified later, store only source URL, lazy-cache relative path, content SHA-256, MIME, byte count, fetch status, and timestamps; do not embed image bytes or absolute workstation paths in product JSON.
- Periodic refresh is full bootstrap followed by change-window delta sync, attribute/relation enrichment, candidate materialization/index/cache validation, and one atomic `active_release` swap. Any failed refresh leaves the last-good release searchable.

## Commit strategy

- Todo별 Conventional Commit을 기본으로 하고 Todo 번호 순서로 선형화함. 병렬 브랜치는 해당 todo 소유 경로만 수정하고 Wave 결합 전에 공통 품질 명령을 재실행함.
- fixture와 문서는 payload·secret·개인정보 검사를 통과한 뒤에만 stage함. `var/`, `.env`, raw live payload, 원본 개발계정 첨부, 사용자의 세 XLSX는 절대 stage하지 않음.
- 작은 수정은 해당 todo commit에 fixup하고, 기능과 테스트를 분리된 commit으로 쪼개지 않음. 구현+테스트가 한 원자 commit임.
- broad repository root의 다른 untracked/modified 파일은 건드리거나 stage하지 않고 이 workspace 경로만 명시적으로 지정함.
